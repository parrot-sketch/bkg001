# Billing / Charge Sheet Domain — Architecture Notes

This project currently models a **charge sheet** as a `Payment` record in the database, with line items stored as `PatientBill` rows.

This document summarizes:
- Current entity relationships (especially to `Patient`)
- What’s working today
- Architectural gaps that can cause inconsistencies
- A recommended “charge sheet as source of truth” design for accuracy + idempotency

## 1) Current Entities & Correlations

### Patient
- Table: `Patient`
- Key: `Patient.id`
- Relationship: `Patient (1) → (N) Payment`

### Charge Sheet (currently: Payment)
- Table: `Payment`
- Key: `Payment.id`
- Optional unique links:
  - `appointment_id` (unique) — one charge sheet per appointment
  - `surgical_case_id` (unique) — one charge sheet per surgical case
- Identifiers:
  - `charge_sheet_no` (unique) — generated by `ChargeSheetService.ensureChargeSheetNo`
- Lifecycle:
  - `finalized_at`, `finalized_by` mark “ready for collections”
- Financial fields:
  - `total_amount`, `discount`, `amount_paid`, `status`, `receipt_number`

### Charge Sheet Line Items (currently: PatientBill)
- Table: `PatientBill`
- Key: `PatientBill.id`
- Relationship: `Payment (1) → (N) PatientBill`
- Item can be either:
  - `service_id → Service` (procedure/consultation/etc), OR
  - `inventory_item_id → InventoryItem` (billable inventory usage)
  - plus special links like `surgical_medication_record_id` (unique) for medication billing correlation.
- Financial fields:
  - `quantity`, `unit_cost`, `total_cost`

### Service Catalog
- Table: `Service`
- Relationship:
  - `Service (1) → (N) PatientBill`
  - `ProcedureServiceLink` links services to procedure categories / procedures

### Inventory Billing Linkage
- `InventoryUsage` can link back to `PatientBill` (billable usage becomes a line item)
- `InventoryConsumptionBillingService` already does idempotent inventory usage application via `external_ref` (unique).

## 2) What “Charge Sheet is the Source of Truth” Means

The charge sheet must be the single, authoritative record of:
- **which billable items exist** (line items)
- **their pricing** at the time of charge
- **the derived totals** (subtotal/discount/total due)

Operationally:
- Clinical staff build the charge sheet (draft).
- Clinical finalizes charge sheet (locks clinical billing content).
- Cashier/frontdesk collects payments against finalized charge sheets.

## 3) Key Risks in the Current Model

### A) Total mismatch risk
If `Payment.total_amount` is not derived from `PatientBill` items, totals can drift.

### B) Payment collection is not event-sourced
`amount_paid` is updated in-place. Retries (network, double-click, client resend) can duplicate payments without an idempotency key.

### C) Money types
Some monetary fields are `Float`, which risks rounding errors over time.

## 4) Recommended Enterprise-Grade Architecture (Incremental)

### Step 1 (Low risk, immediate value)
- Derive `Payment.total_amount` from line items whenever line items are provided/updated.
- Only allow collections when `finalized_at` is set.

### Step 2 (Idempotency & auditability)
Introduce a new table (example):
- `PaymentCollectionEvent`
  - `id` (uuid)
  - `payment_id`
  - `idempotency_key` (unique)
  - `amount`
  - `method`
  - `recorded_by_user_id`
  - `recorded_at`
  - `notes`

Then:
- `Payment.amount_paid = SUM(events.amount)` (derived) or periodically recomputed.
- Receipt numbers become per-event (or still per-payment, but generated once on full settlement).

### Step 3 (Consistency + locking)
Split statuses:
- `ChargeSheetStatus`: `DRAFT | FINALIZED | VOID`
- `SettlementStatus`: `UNPAID | PART | PAID | REFUNDED`

Enforce:
- No editing bill items when `ChargeSheetStatus=FINALIZED`.
- Refunds are modeled as negative events (append-only).

### Step 4 (Money correctness)
Migrate monetary columns to `Decimal(10,2)` consistently for currency.

## 5) Edge Cases to Handle Explicitly
- Partial payments across multiple events
- Overpayment attempts (reject with 409)
- Concurrent collection events (optimistic concurrency or serializable transaction)
- Draft charge sheet accidentally showing in collections queue (filter to finalized)
- Price changes in `Service` after charging (line items store `unit_cost` snapshot, which is correct)
- Inventory usage replays (already handled via `external_ref` in inventory usage service)
